## 1. 背景与问题陈述

### 1.1 现状
组内同时推进多个项目，目前**通过 Excel 逐个管理每个项目的进展**。当前使用的是一张**以"人"为行的组内周报表**，表头为：

> **机型 | 项目 | 是否投入该项目 | 项目角色 | 关键节点 | 项目周目标 | 本周任务 | 每日任务**

即：**多名成员在同一个项目下各自填写进展与任务**（多人协作填报同一项目），**每周开会时按这张表过**。随着项目与人员增多，这种方式越来越难以维护。

### 1.2 痛点（结合现有 Excel）
- **按人组织、项目难拼**：一个项目涉及多名成员、跨越多行，想了解单个项目的整体进展需要跨行拼凑，没有项目维度的统一视图。
- **每日任务散落**：每个人的"每日任务"填在各自格子里，无法集中查看某天全组/某项目的实际进展。
- **历史断档**：周与周靠新建文件/工作表承载，历史进展难以连续追溯。
- **多人协作冲突、无留痕**：同一 Excel 多人编辑易冲突，谁改了哪、何时改的没有记录，出了问题无法追溯。
- **节点不规范**：各项目的"关键节点"靠习惯填写，缺乏统一的 TR 节点基线。
- **状态滞后**：Excel 更新滞后，周会上看到的往往已是过期信息。
- **项目状态不直观**：无法一眼看清所有项目当前的"未开始/进行中/延期/已完成"分布，也缺乏按年/月的整体视图。
- **个人工作量难统计**：想了解某人某月/季/年做了什么、投入多少，只能翻 Excel 手工汇总，绩效考核缺乏客观依据。

### 1.3 解决思路
做一个**内网、组内、轻量**的项目管理工具，替代 Excel：
以 **项目 → TR节点 → 任务 → 进展** 结构承载工作；**多人协作在项目/节点上填报进展**（可关联任务），任务只管"是否完成 + 计划/实际时间"，进展管"每日流水记录"，两者互补；系统**自动汇总**项目周报（周目标 / 本周任务 / 每日明细 / 风险）；内置**华为 TR1~TR6 评审流程**，**立项时自选本次需要的 TR 节点**；提供**项目看板**（年/月视图 + 状态分布）与**个人月/季/年工作情况 AI 自动汇总**（供绩效考核）。周会主视图**按项目组织**（可下钻到人），同时保留**按人**辅助视图，贴合现有习惯。

## 2. 项目愿景与目标

### 2.1 愿景
成为组内统一的"项目真相来源"：打开系统即知所有项目进展，彻底告别 Excel 台账与手工汇总周报。

### 2.2 业务目标（上线后 3 个月）
| 目标 | 说明 | 衡量 |
|---|---|---|
| 替代 Excel | 组内全部在研项目纳入系统 | 项目覆盖率 100% |
| 进展自动汇聚 | 周报由系统自动生成，无需手工汇总 | 周报自动化率 |
| 节点规范 | 项目按 TR 节点推进，评审留痕 | TR 节点覆盖率 |
| 进度透明 | 任意时刻可查看任一项目/节点/任务状态 | 状态更新及时率 |

### 2.3 系统目标（技术，轻量定位）
- 组内规模（≤ 50 人、≤ 50 并发），常规操作流畅（P95 < 1s）。
- 内网私有化部署，数据不出内网。
- 简单可靠，易于维护与备份。

## 3. 项目范围

### 3.1 范围内（In Scope）
- 账号密码登录、管理员/成员两种角色
- 项目管理：新建、编辑、状态、归档、成员
- **项目节点（TR）管理**：基于模板的节点、顺序流转、评审记录
- **任务管理**：挂在 TR 节点下，指派、截止、状态
- **进展填报（日报）**：任务级日报（今日工作 / 明日计划 / 风险问题）
- **自动汇总**：项目日报 → 项目周报
- **多项目总览仪表盘**：一屏看清所有项目阶段与状态
- 项目/节点/任务的动态与操作留痕
- 基础导出（周报导出，用于存档/上报）
- Excel 项目台账导入（迁移历史项目，降低切换成本）

### 3.2 范围外（Out of Scope · 本期不做）
- 即时通讯（IM）、在线文档协作
- 代码托管 / CI-CD 流水线
- 财务、预算、采购管理
- 复杂资源排程算法
- 移动端原生 App（采用响应式 Web，内网浏览器使用）
- SSO / 企业统一认证（内网组内工具，账号密码即可）
- 敏捷迭代（Sprint）/ 燃尽图 —— 本系统以 TR 节点为阶段单位，不引入敏捷迭代
- 独立工时管理模块（工时以"进展填报"形式轻量体现，不做打卡式工时核算）

## 4. 目标用户与角色

系统仅设**两种角色**，权限模型从简：

| 角色 | 描述 | 核心权限 |
|---|---|---|
| **管理员** | 组长 / 指定维护者 | 全部权限：账号管理、项目/模板/节点的配置、TR 评审结论录入、数据备份 |
| **成员** | 组内工程师 | 查看参与的项目；新建/编辑自己负责的任务；填报日报；更新任务状态 |

> 说明：
> - **项目负责人**不是独立角色，而是项目上的一个"负责人"属性（由成员担任），拥有该项目的管理权（编辑项目、管理节点与任务）。
> - **项目成员**上附带两个属性：**是否投入**（对应 Excel 的"是否投入该项目"列）；项目角色按固定角色组维护：**SE（单选 1 人）**、**TPM（单选 1 人）**、**TL/FO（可多选）**、**CodeReview（可多选）**。同一用户可同时承担不同角色，导出时合并到一个“项目角色”单元格并按角色换行展示。
> - 细粒度到字段级的权限控制本期不做（见 §16 开放问题）。

## 5. 核心数据模型（四层结构）

### 5.1 核心数据模型

系统围绕如下结构组织数据。**关键设计：进展挂在项目/节点上（多人协作填报、可关联任务），任务只管"完成与否+时间"。**

```
项目 (Project)
  ├── TR节点 (Node)      ← 华为 TR，立项时自选需要哪几个，来自模板，按顺序流转
  │     └── 任务 (Task)   ← 节点下的"完成项"：是否完成 + 计划/实际时间（体现"这些事做完没、何时完成"）
  └── 进展 (Progress)     ← 项目/节点上的"流水记录"：多人协作填报，每日一条，可关联任务
```

| 实体 | 关键属性（示意） | 职责 |
|---|---|---|
| 项目 Project | **名称（唯一）**、编号（可选，留空自动生成）、**描述**、**机型**、负责人、成员、当前阶段、**项目周目标**、**手动状态（未开始/进行中/延期/已完成/暂停/归档）**、起止 | 管理单元 |
| 项目成员 Member | 项目、成员、**项目角色**、**是否投入** | 投入与角色 |
| TR节点 Node | 所属项目、节点类型、顺序、**计划/实际时间**、状态、评审结论、材料 | 阶段与评审 |
| 任务 Task | 所属节点、标题、指派人、**计划/完成时间**、**是否完成**(未开始/进行中/已完成/延期) | **完成情况跟踪** |
| 进展 Progress | 所属项目/节点、填报人、日期、**今日进展**、明日计划、风险、**关联任务** | **工作流水记录** |

> **两套数据互补**：TR节点/任务表回答"**这些事是否完成、计划 vs 实际时间**"；进展表回答"**每天实际做了什么、谁在做**"。

### 5.2 三层汇报模型（对应现有 Excel）

现有 Excel 的"项目周目标 / 本周任务 / 每日任务"三列，在系统中对应：

| Excel 列 | 系统来源 | 说明 |
|---|---|---|
| **项目周目标** | 项目每周设定的目标 | 负责人每周填写/确认，作周报头部 |
| **本周任务** | 该项目本周推进/完成的任务（含计划 vs 实际时间） | 体现"做完没" |
| **每日任务** | 该项目各成员**每日进展记录**（多人填报，自动带出） | 体现"每天干了啥" |

**汇报卷积关系**：多人每日进展（项目/节点上）→ 按周聚合 + 项目周目标 + 本周任务完成情况 → 自动生成项目周报。

## 6. 华为 TR 流程落地

### 6.1 TR 节点定义（标准基线）
采用华为 IPD 的技术评审（Technical Review）节点作为项目阶段骨架：

| 节点 | 名称 | 评审焦点（参考） |
|---|---|---|
| TR1 | 概念/需求评审 | 需求与产品包需求是否清晰、完整、可行 |
| TR2 | 计划/方案评审 | 总体方案、规格、计划是否合理 |
| TR3 | 开发前评审 | 详细设计、模块设计是否就绪 |
| TR4 | 开发/测试评审 | 实现与测试（如 SDV/SIT）是否达标 |
| TR5 | 发布前评审 | 是否满足发布/验证（如 SVT）准则 |
| TR6 | 量产/收尾评审 | 可交付性、可维护性、收尾结论 |

> 上表为标准参考基线；每个节点的具体名称、评审要素、准入/准出准则**可配置**。

### 6.2 立项自选 TR + 可自定义节点模板
- 系统内置一套 **TR1~TR6 标准模板**。
- **新建项目时，负责人勾选本项目实际需要做的 TR 节点**（如只做 TR1/TR2/TR4，跳过不适用节点），系统据此生成该项目的节点序列。
- 管理员可基于标准模板**派生自定义模板**（增删节点、改名称、改评审要素），以适配不同类型项目（如研发型 / 预研型 / 合作型）。
- 项目执行中，负责人/管理员可调整节点（增删、调整顺序），留痕。

### 6.3 节点流转与评审
- 节点**按顺序流转**（TR1 → TR2 → … → TR6），前一节点通过后方可进入下一节点（必要时管理员可强制流转并留痕）。
- 每个节点记录**评审结论**：通过 / 有条件通过 / 不通过。
- 节点可关联**评审材料（附件）**与**遗留问题项**（可转为后续任务）。
- 节点的**计划时间 vs 实际时间**用于识别延期。

## 7. 核心业务流程

### 7.1 项目全生命周期
```
立项(新建项目/选TR模板) → 按TR节点推进 → 节点评审 → … → TR6 → 收尾归档
```

### 7.2 任务状态机（默认）
```
未开始(Todo) → 进行中(In Progress) → 已完成(Done)
        ↘ 延期(Overdue，计划时间到未完成自动标记) ↗    可回退(留痕)
```
> 任务聚焦"**是否完成 + 计划/实际时间**"；描述性的每日工作内容不在任务上记，统一走进展（见 7.3）。

### 7.3 进展填报与汇总闭环（核心）
```
多名成员在 项目/当前节点 上填每日进展(今日进展/明日计划/风险，可关联任务)
        │
        ▼ 系统按项目聚合多人当日填报
项目当日进展（一条干净时间线，含谁、何时、做了什么）
        │
        ▼ 系统按周聚合 + 项目周目标 + 本周任务完成情况
自动生成项目周报(周目标 / 本周任务完成 / 每日明细 / 风险问题)
        │
        ▼
周会按"项目"逐个过(可下钻到人) / 导出存档上报
        │
        ▼ 系统按人聚合其各项目进展
个人 月/季/年 工作情况 → AI 自动生成绩效总结
```

### 7.4 周会视图（对齐现有习惯）
- **主视图 · 按项目**：一行一个项目，展示 `机型 | 项目 | 状态 | 当前TR节点 | 项目周目标`，点击展开该项目本周任务与每日明细、各成员进展。**默认视图**，替代现有按人 Excel。
- **辅助视图 · 按人**：一行一个成员，展示该成员各项目的 `是否投入 | 项目角色 | 本周任务 | 每日进展`，用于逐个过个人。与现有 Excel 视角一致，平滑过渡。
- 两种视图同源数据、可一键切换；周与周自动连续，历史可追溯、变更有留痕。

### 7.5 TR 评审流程
节点任务完成 → 发起评审 → 录入评审结论与材料 → （有条件通过/不通过则产生整改任务）→ 通过后进入下一节点。

## 12. 风险与缓解

| 风险 | 影响 | 概率 | 缓解 |
|---|---|---|---|
| 成员不习惯、仍用 Excel | 采用失败 | 中 | 组长推动、提供 Excel 导入、门槛做到极低、先小范围试点 |
| 进展填报负担重 | 抵触/敷衍 | 中 | 项目级填报从简、可关联任务但不强制、未填提醒 |
| AI 绩效总结质量/准确性不足 | 考核失真、不信任 | 中 | AI 总结标注数据来源、可编辑校对、支持重新生成、考核以人工确认为准 |
| AI 接口（OpenAI 兼容 API）异常/限流 | AI 功能暂时不可用 | 低 | 后端代理做超时/重试/限流控制；降级为模板化汇总；不影响核心填报与看板 |
| TR 流程与实际打法不符 | 流程空转 | 中 | 模板可配置、立项自选 TR、先按现状建模板再逐步规范 |
| 需求蔓延 | 进度延误 | 中 | MoSCoW 优先级、MVP 先行、变更控制 |
| 数据丢失 | 台账受损 | 低 | 定期备份、导出存档、留痕可恢复 |

**变更控制**：范围/需求变更 → 申请 → 评估影响 → 审批 → 更新版本与基线。

## 13. 依赖与约束

- **部署环境**：内网服务器（应用 + 数据库 + 附件存储），无需外网。
- **AI 能力**：内网可直接请求 **OpenAI 兼容 API**（LLM 接口）；由后端代理调用，API Key 存于服务端；无 AI 时降级为模板化汇总。
- **人力**：开发、（兼）测试、（兼）UI、组长（产品/验收）。
- **技术约束**：须满足审计留痕要求；架构预留扩展（项目级进展→周报汇总、模板化、AI 总结）。
- **业务约束**：须兼容组内现有 Excel 工作流，支持平滑迁移。
- **外部依赖**：内网基础设施 + 内网可达的 OpenAI 兼容 API。

## 16. 待解决问题（Open Questions）

> 已对齐项：
> - **周会视图** = 按项目为主、按人为辅；**周报** = 项目周目标 / 本周任务 / 每日明细 / 风险问题。
> - **进展模型** = 进展挂**项目/节点**（多人协作、可关联任务）；任务管"完成+时间"，进展管"流水"。
> - **看板** = 年/月视图 + 未开始/进行中/延期/已完成/暂停状态分布（状态手动配置）。
> - **个人绩效** = 月/季/年工作情况，AI 自动生成总结供考核。
> - **TR 节点** = 立项时**自选**本次需要的节点。
> - **AI 能力** = 内网直接请求 **OpenAI 兼容 API**，后端代理调用，无 AI 时降级为模板汇总。
>
> 以下为仍待确认项：

1. **TR 节点的标准定义**：组内各项目实际使用的 TR 阶段划分与评审要素，需收集后固化为内置模板（建议提供 1~2 个现有项目 Excel 作为模板参考）。
2. **是否需要"字段级"权限**？（如：仅管理员可改评审结论、负责人可改节点时间）——本期默认按 §4 从简。
3. **周报的栏目口径**：除"周目标/本周任务/每日明细/风险"外，是否还需"里程碑达成 / 资源投入 / 质量"等栏目？（影响周报模板配置）
4. **AI 接口细节**：OpenAI 兼容 API 的 base_url / 模型名 / 配额与限流 / 是否需脱敏（如项目代号替代真名）？（架构设计时按可配置预留）
5. **历史项目迁移范围**：是否需要把 Excel 里的历史进展一并迁入，还是只迁项目/节点/任务骨架？
6. **"有条件通过"的整改跟踪**：评审问题项是否强制闭环（需全部关闭才能进入下一节点）？
7. **部署形态细节**：单机部署即可，还是需考虑内网多机/主备？
