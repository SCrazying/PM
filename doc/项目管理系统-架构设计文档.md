## 1. 引言与设计目标

### 1.1 设计目标
- **轻量可落地**：单机/少量服务器即可运行，1~2 名全栈可开发与维护。
- **贴合业务**：忠实实现策划书的数据模型（项目 → TR节点 → 任务 / 进展）与核心闭环（项目级多人进展 → 自动周报 → 看板/周会 → AI 绩效）。
- **可配置**：TR 模板、状态枚举、周报栏目、AI 接口均为配置项，不改代码即可调整。
- **可演进**：模块化 + 清晰的表设计，支撑后续移动端、IM 集成、资源负载等扩展。

### 1.2 设计约束
- 内网私有化部署，无外网依赖；AI 走内网可达的 OpenAI 兼容 API。
- 规模：≤ 50 用户、≤ 50 并发、单项目数百任务、进展数据随时间持续增长。
- 关键操作须审计留痕；数据可备份恢复（RPO ≤ 24h，RTO ≤ 4h）。

### 1.3 名词约定
本文与策划书一致：项目(Project) / TR节点(Node) / 任务(Task) / 进展(Progress) / 周目标(WeeklyGoal) / AI 总结(AiSummary)。

## 2. 技术选型

### 2.1 推荐方案（轻量全栈）

| 层 | 推荐 | 选型理由 |
|---|---|---|
| 前端 | **Vue 3 + Vite + Element Plus + Pinia** | 中文企业后台主流；表格/表单/看板/日期组件丰富，契合"表格密集型"管理工具 |
| 后端 | **Python 3.11 + FastAPI** | 开发效率高；Excel 导入导出生态成熟（openpyxl）；调 OpenAI 兼容 API 方便；自带 OpenAPI 文档 |
| 数据库 | **PostgreSQL 14+** | 稳定、支持 JSON 字段（存审计详情/AI 快照）、窗口函数利于汇总统计 |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 与 FastAPI 配套；迁移可版本化 |
| 认证 | JWT（access + refresh） | 无状态、轻量；内网组内够用 |
| 密码 | bcrypt / argon2 | 行业标准散列 |
| 文件存储 | 本地磁盘（+ 可选 MinIO） | 单机即可；后续可平滑切对象存储 |
| AI 调用 | 后端 httpx 代理调 OpenAI 兼容 API | base_url / model / api_key 全配置化 |
| 报表导出 | openpyxl(Excel) / python-docx(Word) / 前端打印或 weasyprint(PDF) | 覆盖周报/绩效导出 |
| 后台任务 | APScheduler（轻量）或 Celery | 逾期检测、未填提醒、周报预生成 |
| 部署 | Docker + docker-compose + Nginx | 一键部署；反向代理 + 内网 HTTPS |

### 2.2 备选与取舍

| 项 | 备选 | 何时选用 |
|---|---|---|
| 后端 | NestJS (Node) / Spring Boot (Java) | 组内主力为 JS/Java 栈时；Spring Boot 适合未来与更多企业系统集成 |
| 数据库 | MySQL 8 | 组内已有 MySQL 运维经验；功能完全够用 |
| 数据库 | SQLite | 仅单人试用/演示；**不建议生产**（并发与备份受限） |
| 前端 | React + Ant Design | 组内 React 更熟时 |
| 认证 | Session + Cookie | 更简单，但多端/扩展性略差 |

> **决策建议**：若组内无既定栈，按推荐方案（Vue3 + FastAPI + PostgreSQL）。最终以使用方拍板为准，本文库表与接口设计与具体语言解耦，换栈不影响数据模型。

## 3. 系统架构

### 3.1 架构风格
单体应用（Modular Monolith）+ 前后端分离。
- 轻量定位下不引入微服务；模块内聚、边界清晰，未来如需拆分成本低。
- 前端 SPA 通过 REST API 与后端交互；后端内部分层。

```

### 4.2 表结构（字段级）

> 通用字段：`id` 统一为主键（BIGINT 自增，全库一致）；各表含 `created_at`，标注 `updated_at` 的有更新时间。

#### 4.2.0 逻辑删除（软删）统一约定 —— 解决"声明了但没落地 + 与唯一约束冲突"
**1. 逐表软删清单**
- **软删**（加 `is_deleted boolean NOT NULL DEFAULT false` + `deleted_at datetime NULL`）：`project`、`project_node`、`task`、`progress`、`project_member`、`project_weekly_goal`、`progress_task_link`、`attachment`。
- **只增不删**：`node_review`、`audit_log`（评审与审计不留"删除"）。
- **覆盖式更新**（不软删，同周期 upsert 覆盖）：`ai_summary`、`project_weekly_goal` 内容、`config`；`notification` 物理删除/定期清理。

**2. 唯一约束改造（软删兼容，核心）** —— 普通 UNIQUE 对软删行仍生效，会导致"软删后无法重建"。统一改为**部分唯一索引**（PostgreSQL 无"部分唯一约束"，用部分唯一索引实现）：
```sql
CREATE UNIQUE INDEX ux_project_code   ON project(code)                       WHERE NOT is_deleted;
CREATE UNIQUE INDEX ux_member         ON project_member(project_id,user_id)  WHERE NOT is_deleted;
CREATE UNIQUE INDEX ux_weekly_goal    ON project_weekly_goal(project_id,week_start) WHERE NOT is_deleted;
```
**3. 级联与过滤语义**
- **级联**：父软删则级联软删直接子表（删 project → 级联软删其 node/task/progress/member/weekly_goal/attachment；删 node → 级联软删其 task/节点级 progress/attachment）。`node_review`/`audit_log` 不级联删。
- **过滤**：Repository 层对所有业务查询统一追加 `is_deleted=false`（SQLAlchemy 全局过滤/事件）；周报/看板/汇总/AI 引擎读取同样生效；"含已删"查询需显式 opt-out。
- **恢复/硬删**：`restore` 清 is_deleted/deleted_at 并级联恢复；物理删除仅管理员、先级联清理子行并记 audit_log。
- **接口**：各资源补 `DELETE`（软删）、`POST /{id}/restore`（恢复），管理员可硬删。

**4. 索引同步**：§4.3 索引均带 `WHERE NOT is_deleted`（部分索引），避免软删行进入常用索引。

> **角色约束（应用层保证）**：
> - **SE / TPM**：每个项目**各最多 1 人**（单选，换人即覆盖原角色）。
> - **TL/FO / CodeReview**：每个项目**可多人**（多选）。
> - 角色分配用户**自动进入 project_member**（保证能填报进展/领任务），但不改变其投入状态。
> - 编辑项目时传入完整角色集合，后端以本次集合**整体替换**（清空即解除角色）。
> - 负责人（owner）仍由 `project.owner_id` 管理，不占用上述角色。

> **负责人一致性（强制）**：`project.owner_id` 必须存在于该项目的 `project_member` 中（由应用层在建项/变更负责人时同事务写入/更新成员行）。否则成员校验会拦截负责人填报/操作，按人聚合也会漏掉负责人。**is_invested 的时态说明**：该字段表示"**当前**是否投入"；历史周的投入状态以"该周是否有进展/任务记录"辅助推断（见 §12.2 开放问题，若需精确按周投入可后续加 `member_invest_history`）。

## 5. 核心引擎设计

### 5.1 汇总引擎（进展 → 周报）

**输入**：某项目某周的 `project_weekly_goal` + 该周 `progress`（多人，按 `progress_date`）+ 本周任务集合。
**输出**：项目周报（周目标 / 本周任务 / 每日明细 / 风险问题）。

处理逻辑：
1. **取周目标**：按 (project_id, week_start) 取本周目标（week_start 已按周界配置规整）；缺省提示负责人补填。
2. **聚合本周任务**（纳入口径，取并集，避免漏"计划本周做"）：满足其一即纳入——
   - 计划区间与本周相交：`planned_start <= 周末 AND planned_end >= 周一`（含"计划本周做但还没碰"的进行中任务）；
   - 或本周内有状态变更 / 实际完成时间落在本周；
   - 标注"是否完成 + 计划 vs 实际时间"。
3. **聚合每日明细**：按 `progress_date` 分组、再按 author 分组的进展列表（谁、何时、做了什么）。
4. **汇聚风险**：合并本周各进展的 risk 字段（去重/归并）。
5. **组装周报**：四层栏目 → 结构化 JSON → 渲染/导出。

组内周报：
- **按项目视图**：对每个 ACTIVE 项目（未开始/进行中/延期/暂停，见 §5.2）跑上述汇总，一屏/一表罗列（机型/项目/状态/当前TR/周目标），可下钻。
- **按人视图**：对每个成员，聚合其本周在各项目的进展（按 progress_date）+ 是否投入/项目角色 → 一行一人。

> 实现要点：纯 SQL 聚合 + 应用层组装；当周快照缓存提升周会加载速度。**周界定（默认周一~周日）存 config `report.week_start_dow`，全系统（汇总/周目标/看板）统一读此配置**。

### 5.2 看板与项目状态（M7：状态手动化 + 健康度下线）
- **项目状态 = 手动配置**，不随 TR 流程自动派生，共 6 个值：`not_started 未开始 / in_progress 进行中 / delayed 延期 / completed 已完成 / suspended 暂停 / archived 归档`。
- **看板列判定（唯一规则，一个项目只进一列，列=项目状态）**：
  | 列 | 判定 |
  |---|---|
  | 未开始 | status = not_started |
  | 进行中 | status = in_progress |
  | 延期 | status = delayed |
  | 已完成 | status = completed |
  | 暂停 | status = suspended（默认折叠，可展开） |
  | （归档） | status = archived 默认不在看板，列表/周会可查 |
- **状态维护**：项目列表「状态」列**内联编辑**、项目表单可选；仅负责人/管理员可改（应用层校验，6 值白名单）；置 `archived` 时补记 `archived_at`。归档/恢复接口保持（archive=置 archived+记 archived_at）。
- **健康度已下线（M7）**：不再派生 `health`（删除 compute_health / 每日兜底重算 / `/board/refresh-health` 端点）；`project.health` 字段**保留不删**（历史值不回写、不丢失），前端不再展示。"延期"改由**手动状态 delayed** 表达。
- **"在研/ACTIVE"口径** = `{not_started, in_progress, delayed, suspended}`：工作台待办（my_todo）、周会按人/按项目聚合、周会前端加载统一使用该口径（不再只取 in_progress），保证未开始/延期项目也能在周会与工作台看到。
- **年/月视图**：按项目当前节点的 planned/actual 时间或项目起止落到对应年/月分桶；按月展示该月活跃/到期项目分布。

### 5.3 节点流转引擎
- **立项生成**：建项时勾选的 TR 节点（来自模板）→ 实例化为 project_node 序列（按 sequence，UNIQUE(project_id,sequence)）；**模板节点若有默认子节点（tr_template_subnode），同步实例化为该节点实例的子节点**（parent_id=节点实例，planned_end 默认取节点 planned_end）。
- **当前 TR（current_node_id 口径）**：= 序列中第一个 status ∉ {passed} 的节点（即"当前待推进节点"）；全部 passed 则取最后一个。由本引擎在流转/调整时维护到 project.current_node_id，供看板/列表/周报直接读。
- **节点状态迁移表**（补全回退/重做边，解决死锁）：
  | 从 → 到 | 触发 | 角色 | 留痕 |
  |---|---|---|---|
  | not_started → in_progress | 开始节点工作 | 负责人/管理员 | - |
  | in_progress → pending_review | 发起评审 | 负责人/管理员 | - |
  | pending_review → passed | 评审 pass / conditional_pass | 管理员录评审 | node_review |
  | pending_review → failed | 评审 fail | 管理员 | node_review |
  | **failed → in_progress** | 打回整改重做 | 负责人/管理员 | audit_log |
  | **failed → pending_review** | 整改完成后重新送审 | 负责人/管理员 | - |
  | **pending_review → in_progress** | 撤回送审 | 负责人/管理员 | - |
  | **passed → in_progress** | 纠正误判（reopen） | **仅管理员** | audit_log 强制 |
- **conditional_pass 整改闭环（默认硬闭环，承接策划书 §16-Q6）**：
  - 评审 conditional_pass 后节点 status 记 **passed**，但派生 **rectifying（整改中）** 标记：存在未完成整改任务（task.source_review_id 指向该次评审且 status!=done）时为真。
  - **流转门控（不变量）**：仅当本节点最新评审 = pass，**或**（= conditional_pass 且其全部整改任务均 done）时，才允许进入下一节点；否则阻止并列出未关闭整改项。管理员 force_transition 可绕过但须记 audit_log.force_transition（含前后值与理由）。
  - 看板/详情页对 rectifying 节点展示"整改中"徽标。
  > 若使用方在 §16-Q6 选择"软标记（不阻断，仅提示）"，仅需移除此门控、保留 rectifying 打标，改动面最小。
- **顺序流转约束**：默认须前一节点 passed 方可推进下一节点；force_transition 仅管理员、记审计、不可越过项目归档/完成约束。
- **延期**：节点 planned_end 到期未 passed → 标延期（派生，参与 health 计算）。
- **调整**：执行中增删/调序节点（留痕，维护 sequence 唯一与 current_node_id）。

### 5.3a 节点完成情况更新机制（M4 · 精简版）

> 目标：让负责人/管理员能**直接在节点上更新完成情况**，方便早会当场勾选更新，流程尽量轻。

#### 1. 更新方式（两种，均由负责人/管理员操作）
| 方式 | 操作 | 结果 |
|---|---|---|
| **A. 直接标记完成** | 在节点任务面板点"完成节点" | 节点状态 → `passed`，记 actual_end |
| **B. 评审驱动** | 录入评审结论（pass/conditional_pass/fail） | 自动驱动节点状态（见 §5.3） |

> 取消原"成员批量反馈 + 负责人确认 + 通知"的复杂流程。节点完成由负责人/管理员直接定，成员只负责把各自任务做完。

#### 2. 完成度自动计算（展示辅助）
- **节点完成度** = 已完成任务数 / 总任务数（%），辅助负责人判断是否可标记完成。
- **项目完成度** = 已通过节点数 / 总节点数（%），看板/列表展示。
- 完成度为展示指标，不强制门控——**负责人可在任务未全做完时也直接完成节点**（灵活性优先，适应早会快速更新）。

#### 3. 权限与留痕
- "完成节点"仅 **负责人 / admin** 可操作（owner 档），成员不可见该按钮。
- 直接完成节点记 audit_log（action=update，target=node，status→passed）。
- 完成节点后自动维护 `project.current_node_id`（推进到下一未通过节点）。

#### 4. 接口
| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | /nodes/{id}/complete | owner | **直接完成节点**（置 passed + actual_end + 维护 current_node_id） |
| GET | /nodes/{id}/completion | login | 节点完成度（已完成任务/总任务） |
| GET | /projects/{id}/completion | login | 项目完成度（已通过节点/总节点） |

#### 5. 与现有设计的关系
- 复用 §5.3 状态机；`complete` 即 not_started/in_progress/pending_review/failed → passed 的便捷直达，**完成后自动激活下一节点（置 in_progress）**。
- **推进门控（适配无评审环境）**：`进入下一节点`/`advance` 仅要求本节点 `status=passed` 即可放行，**不强制要求评审记录**；评审为可选增强——若存在评审结论 conditional_pass 且整改未关闭、或 fail，仍拦截提示。有正式评审流程时可走 `add_review`（pass/conditional_pass 同样置 passed）。
- current_node_id 随之更新，无需额外逻辑（health 已下线，见 §5.2）。

### 5.3b 节点子节点管理（M6 新增）

> 目的：让每个 TR 节点下的工作可**动态拆分为子节点**（如 TR2 下拆"方案A/方案B/评审材料"），单独跟踪完成情况；周会视图可在当前节点下直接查看并点击完成。

#### 1. 数据模型（复用 project_node）
- `project_node.parent_id` 自引用：NULL=顶层 TR 节点；非 NULL=该节点的子节点。
- 子节点字段：name（名称）、planned_end（**截止时间**）、status（not_started / in_progress / **done**）、actual_end（完成时间，置 done 时记录）。
- 子节点**不参与**：项目 current_node_id 推进、节点进度条（el-steps）、项目完成度（仍按顶层节点算）。它们只作为当前节点内部的跟踪清单。

#### 2. 完成状态更新
- 子节点完成 = 置 status=done + 记 actual_end；未完成且 planned_end<today → 派生"延期"标识。
- **谁可更新**：项目成员均可将子节点标记完成（周会当场点）；编辑/新增/删除子节点限负责人/管理员。
- 子节点全部 done 时，前端提示"该节点子项已全部完成，可完成节点"，但不强制（与 M4 完成节点灵活原则一致）。

#### 3. 接口
| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | /nodes/{id}/subnodes | owner | 在节点下添加子节点（{name, planned_end}） |
| GET | /projects/{id}/nodes | login | 节点列表含各节点 subnodes[]（子节点数组） |
| PATCH | /subnodes/{id} | owner | 编辑子节点名称/截止时间 |
| PATCH | /subnodes/{id}/status | member | 更新子节点完成状态（{status: done/in_progress}） |
| DELETE | /subnodes/{id} | owner | 删除子节点 |

#### 4. 周会视图（M6 增强：子节点列 / 每日进展列 / 风险关闭）
- 主表新增 **"子节点"列**：显示当前节点子节点，**每项按"截止时间 + 子节点名称"格式**（如 `08-15 方案A`），点击子节点切换完成状态并**标绿**（完成项绿色勾/绿色背景），局部同步更新。
- 主表新增 **"每日进展"列**：显示本周每日进展摘要（`MM-DD 作者: 内容`，取最近若干条）。
- **风险问题可点击关闭/重新打开**：调 `PATCH /progress/{id}/risk-resolve`；已关闭风险置灰并标注"已解决"，不再计入 health 的 at_risk 判定与风险待办。
- 周报 `risks` 项带 `progress_id`、`resolved` 字段，供前端关闭操作与置灰展示。

### 5.4 AI 引擎（个人绩效生成）
流程：
```
触发(个人页"生成总结"，仅本人或管理员可触发，见 §8)
  → 写 ai_summary 占位行(status=generating)，(user,period)唯一键防并发重复
  → 异步任务：
     收集数据：该成员周期内的 progress + 完成任务 + 参与项目/角色/投入
     (超长控制：进展按周期截取最近/最相关 N 条 + 其余按项目聚合统计，避免超上下文)
     (可选)脱敏：项目代号替代真名
     组装 Prompt（指令 + 结构化数据 + 输出格式；prompt 模板存 config，含版本号）
     后端代理调 OpenAI 兼容 API (httpx, base_url/model/key 可配置, 超时/重试/限流)
     成功 → 更新行 status=generated + content + source_snapshot
     失败 → status=failed + error；前端降级为"模板化汇总"(不润色)
  → 前端轮询/查询该 (user,period) 的 ai_summary 状态
  → 展示 generated → 可编辑(写 edited_content, status=edited)/导出/重新生成(覆盖 content, 保留 edited 提示)
```
- **数据来源可溯**：`source_snapshot` 记录**进展/任务 ID + 当时文本摘要 + period + prompt版本 + 模型参数**，即便原数据后被改/删，也能复盘"这份总结基于哪批数据、哪版 Prompt 生成"。
- **状态机**：generating → generated → edited / failed（failed 与"降级模板汇总"区分：failed 表示无 AI 产出，模板汇总为前端兜底展示，可另存为 generated 并标注 source=template）。
- **Prompt 模板**存 config（含版本），可调；调用日志脱敏。

## 7. 接口规范（REST API）

### 7.1 约定
- Base：`/api/v1`；认证：`Authorization: Bearer <token>`。
- 响应统一：`{ code, message, data }`；错误码：0 成功，4xx 客户端错误，5xx 服务端错误。
- 列表统一分页：`?page=&size=`，返回 `{ list, total, page, size }`。
- 时间格式：ISO8601；日期 `YYYY-MM-DD`。
- **幂等**：写接口支持 `Idempotency-Key` 请求头（弱网重试防重复创建）；归档等互斥操作拆分为两个端点。
- **权限标注**：每接口标注所需权限——`admin`=仅管理员；`owner`=项目负责人或管理员；`member`=项目成员；`login`=任意登录用户；`self`=仅本人或 admin。（详见 §8 三档角色）

## 8. 安全设计

### 8.1 角色与授权（三档：系统角色 + 项目级角色）
系统在"管理员/成员"两角色之上，叠加**项目负责人**这一项目级权限（对应策划书 §4：负责人是项目上的属性，拥有该项目管理权）：

| 权限档 | 判定 | 能做什么 |
|---|---|---|
| **admin** | user.role = admin | 全部权限 + 系统配置、用户/重置密码、模板、审计、备份、强制流转 |
| **owner（项目负责人）** | project.owner_id = 本人 或 admin | 该项目的编辑、归档、成员管理、周目标、节点调整/流转/评审 |
| **member（项目成员）** | 在该项目 project_member 中 | 该项目的任务/进展 CRUD（进展仅本人可改） |
| **login（登录即可）** | 任意登录用户 | 查看项目列表/看板/周报/时间线（见 8.3 可见范围） |
| **self（仅本人或 admin）** | user_id = 本人 或 admin | 个人绩效汇总/AI 总结的查看、生成、编辑、导出 |

> 授权在**接口层逐请求校验**（见 §7 权限列），项目级操作先校验 project_member/owner 归属，防水平越权。

### 8.2 安全措施
| 方面 | 措施 |
|---|---|
| 认证 | JWT（access 短时效 + refresh）；**refresh_token 持久化（auth_token 表）可吊销**——登出/改密/管理员重置即失效；**登录失败计数 + 锁定**（user.failed_login_count / locked_until） |
| 授权 | 8.1 三档模型，接口级校验 |
| 密码 | bcrypt/argon2 散列，绝不存明文；重置后临时密码首登强制改 |
| 传输 | 内网 HTTPS（自签/内网 CA 证书） |
| 注入/XSS/CSRF | ORM 参数化查询；输出转义；CORS 白名单；纯 Bearer（无 Cookie 则 CSRF 风险低） |
| 越权 | 项目级校验成员/owner 归属；**personal 域校验 user_id=本人或 admin**（防遍历绩效/盗刷 LLM 配额） |
| 审计 | 关键操作（增删改、评审、强制流转、登录、导入、配置变更、**导出/下载、重置密码、备份**）写 audit_log（diff + IP） |
| AI Key | 仅存服务端（环境变量/加密 config），前端永不接触；**GET /config 不返回敏感项的值**；调用日志脱敏 |
| 数据脱敏 | AI 外发数据可选项目代号替代真名（可配置） |
| 附件 | 类型/大小白名单，存非 Web 直读目录，经鉴权接口下载 |

### 8.3 成员可见范围（调和策划书"查看参与的项目"与"看板一屏看全"）
- **读（查看）**：组内为透明协作环境，**登录用户可查看所有项目的列表/看板/周报/进展时间线**（支撑 BOARD-01/RPT-03/周会主视图"一屏看全"）。
- **写（操作）**：仅能操作**自己参与的项目**的任务/进展（member 校验）。
- **敏感数据**：个人绩效（AI 总结、个人汇总）仅 **本人 + admin** 可见（self 档），不对全员开放。
> 即"看全、改己、绩效私有"。若使用方要求项目级读隔离，可在 §12.2 提为开放项，改为 member 仅见参与项目。

## 9. 部署与运维

技术栈已确认：**Vue 3 + FastAPI + PostgreSQL**。提供**两种部署方式**：方式一 Docker（有 Docker 环境时首选，最省事）；方式二 离线/原生部署（内网无 Docker 时使用）。两种方式运行同一套应用，仅环境装配不同。

### 9.0 部署前提
| 项 | 要求 |
|---|---|
| 服务器 | 内网 Linux（CentOS/Rocky/Ubuntu）或 Windows Server；2C4G 起步（≤50 用户） |
| Python | 3.11（离线部署用，含 venv） |
| Node | 仅构建前端时需要（18+），运行期不需要（前端构建产物为静态文件） |
| PostgreSQL | 14+ |
| Nginx | 反向代理 + 静态托管 + TLS |

### 9.1 方式一：Docker 部署（首选）
- `docker-compose` 编排 3 个容器：`nginx` / `backend`(FastAPI+uvicorn+APScheduler) / `postgres`。
- 数据卷：PG 数据、附件目录、备份目录（命名卷持久化）。
- 内网 HTTPS：Nginx 终止 TLS。
- **内网无法访问 Docker Hub 时**：在能上网机器 `docker save` 导出 `postgres:14`、`python:3.11`、`nginx:alpine` 及构建好的应用镜像为 tar → 拷到内网 `docker load` 导入 → `docker-compose up -d`。
- 启动后自动执行 Alembic 迁移建表、写入内置 TR 模板等种子数据。

```yaml
# docker-compose.yml（示意）
services:
  db:
    image: postgres:14
    environment: { POSTGRES_USER: pm, POSTGRES_PASSWORD: ${DB_PASSWORD}, POSTGRES_DB: pm_system }
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
  backend:
    build: ./backend            # 或离线导入的已构建镜像
    environment: { DATABASE_URL: postgresql://pm:${DB_PASSWORD}@db:5432/pm_system, AI_BASE_URL: ${AI_BASE_URL}, AI_API_KEY: ${AI_API_KEY} }
    depends_on: [ db ]
  nginx:
    image: nginx:alpine
    ports: [ "443:443" ]
    volumes: [ "./frontend/dist:/usr/share/nginx/html", "./nginx.conf:/etc/nginx/conf.d/default.conf", "./certs:/etc/nginx/certs" ]
    depends_on: [ backend ]
volumes: { pgdata: {} }
```

### 9.2 方式二：离线 / 原生部署（内网无 Docker）
核心思路：**在能上网的机器上把所有依赖打成离线包，拷到内网一次性安装**。交付物为一个可拷贝的"部署包"目录。

**部署包内容**
```
pm-deploy/
├── backend/                 # 后端源码
│   ├── app/                 # FastAPI 应用
│   ├── requirements.txt
│   └── wheels/              # pip download 下来的全部依赖 wheel（离线安装）
├── frontend/dist/           # 前端构建产物（静态文件，联网机器上 npm build 生成）
├── postgres/                # PostgreSQL 离线安装包（Windows 安装器 / 绿色解压版）
├── nginx/                   # Nginx 安装包 + 配置
├── db/
│   ├── schema.sql           # 建库脚本（18 表，备查）
│   └── seed.sql             # 内置 TR 模板/管理员账号等种子数据
├── scripts/
│   └── init_db.ps1          # Windows 数据库初始化（幂等建用户/库 → Alembic 迁移 → 种子数据）
└── docs/部署手册.md
```

**安装步骤（Windows 示例，数据库初始化走脚本）**
1. **装 PostgreSQL**：官方 Windows 安装器，记下 postgres 超级用户密码；无需手动建库。
2. **装后端依赖**：`python -m venv venv && venv\Scripts\pip install --no-index --find-links=backend\wheels -r backend\requirements.txt`（`--no-index` 强制离线，全部从本地 wheels 装）。
3. **初始化数据库（一键）**：`powershell -ExecutionPolicy Bypass -File deploy\scripts\init_db.ps1 -PgPassword <postgres密码>`——自动建 `pm` 用户与 `pm_system` 库、执行 Alembic 迁移建表、写入种子数据（内置 TR 模板/管理员/配置）。
4. **部署前端**：`frontend\dist` 拷到 Nginx 站点目录。
5. **配 Nginx**：`/ → 前端静态`、`/api/* → 127.0.0.1:8001`、TLS 证书。
6. **常驻后端**：NSSM / 任务计划程序托管 `uvicorn app.main:app --host 127.0.0.1 --port 8001`（APScheduler 随进程跑定时任务）。
7. **配环境变量**：`DATABASE_URL`、`AI_BASE_URL`、`AI_API_KEY`、`JWT_SECRET` 等（写入 .env，init_db.ps1 已自动补全 DATABASE_URL）。

> Linux 原生部署可参考上述步骤移植；`deploy/scripts` 当前提供 Windows 的 `init_db.ps1`（Linux 的 bash 安装/备份脚本已移除）。

### 9.3 备份与恢复（RPO ≤ 24h，RTO ≤ 4h）
- **数据库**：每日定时 `pg_dump` 到备份目录（Docker 用 cron 容器 / Windows 用任务计划程序），保留最近 N 份（可配置）。
- **附件**：每日增量同步到备份目录。
- **恢复**：`createdb` 重建库 + `pg_restore`/`psql -f` 导入备份；定期演练。
- 备份可在 admin 页面手动触发 + 下载（接口 `/backup`、`/backups`、`/backups/{id}/download`，见 §7）。

### 9.4 日志与监控
- 应用日志（结构化）+ Nginx 访问日志；错误告警（可选邮件/webhook）。
- 轻量监控：磁盘、进程存活（Docker healthcheck / systemd + 简单探活脚本）。

### 9.5 Excel 台账导入
- 提供导入模板，兼容现有表头：机型/项目/是否投入/项目角色/关键节点/项目周目标/本周任务（每日任务作为可选历史字段）。
- **预览 → 确认两步**（接口 `/import/excel/preview`、`/import/excel/confirm`）；映射规则可配置；导入记 audit_log；幂等键防重复入库。

### 9.6 项目台账 Excel 导出（M5）
- 导出范围：按指定周（默认当前周）导出组内在研/可见项目，每个**项目成员一行**（同一项目下 SE/TPM/TL-FO/CodeReview 成员各占一行，同一用户多角色拆多行）。
- 固定列顺序：`机型 | 项目 | 是否投入 | 项目角色 | 关键节点 | 周目标 | 本周任务`。
- **项目角色单元格格式**（同项目按角色分组合并到一个单元格、每角色一行）：
  ```
  SE: 张三
  TPM: 李四
  TL/FO: 王五、赵六
  CodeReview: 钱七、孙八
  ```
  规则：角色顺序固定 SE→TPM→TL/FO→CodeReview；SE/TPM 各一行、TL/FO 和 CodeReview 各一行、多用户顿号连接；空角色不输出；同时输出 `负责人: 用户名` 行确保负责人导入不丢失。
- 其中：关键节点取项目当前 TR 节点；周目标取 `project_weekly_goal`；本周任务取该成员负责/参与项目任务集合与本周进展摘要。
- 工作簿格式：首行冻结、自动筛选、表头加粗/底色、单元格垂直居中、文本自动换行；列宽固定为 `14/24/12/22/18/30/52`，避免长文本挤压或截断。
- 文件名：`项目台账_YYYY年第WW周.xlsx`；导出操作记录 `audit_log(action=export)`。
- 导入兼容：导入解析"项目角色"单元格时，按 `负责人:`/`SE:`/`TPM:`/`TL/FO:`/`CodeReview:` 前缀分组、顿号分隔还原成员与角色；SE/TPM 单选覆盖、TL/FO/CodeReview 多选追加；兼容实际换行与字面量 `\n`/`\N`。详见《项目角色管理与导入导出方案》。

## 11. 扩展性设计

> 轻量定位下遵循 **YAGNI**：只保留"低成本、高确定会用到"的扩展点，避免过度抽象抬高引擎层复杂度。

| 扩展点 | 保留方式 | 取舍说明 |
|---|---|---|
| TR 模板 | tr_template/tr_template_node 表 + 建项自选 | **保留**（策划书 Must，核心流程） |
| AI 配置 | config 存 base_url/model/api_key/prompt_template | **保留**（PERS-02 Must 需要），**不做 provider 抽象层**（只有一种实现，YAGNI） |
| 周界口径 | config `report.week_start_dow` | **保留**（低成本，避免口径写死） |
| 周报栏目 | 汇总引擎按固定四层栏目组装 | **固定栏目**（策划书已定三层+风险，不做运行时栏目模板引擎，YAGNI）；栏目调整走改代码 |
| 状态枚举 | 代码枚举 + 数据库 CHECK | **不存 config 运行时改**（YAGNI，状态机改动本就需评审） |
| 自定义字段 | 关键表预留 jsonb `extra` | **可选保留**（成本极低，真需要时启用） |
| 提醒渠道 / 多端 | notify 模块、REST 与前端解耦 | 结构上**不堵死**（后续可加 IM webhook / 移动 H5），但本期不实现抽象层 |

## 12. 技术决策与开放问题

### 12.1 已确认的技术决策
1. **技术栈**：✅ 已确认 —— **Vue 3 + FastAPI + PostgreSQL**。
2. **数据库**：✅ 已确认 —— **PostgreSQL**（软删唯一索引用 PG 部分/表达式索引，见 §4）。
3. **主键策略**：✅ 默认自增 BIGINT。
4. **部署方式**：✅ 已确认 —— **提供 Docker 与离线/原生两种方式**（内网无 Docker，见 §9）。

### 12.2 开放技术问题（已给默认结论，待确认）
4. **AI 接口参数**：base_url / model / 配额 / 限流 / 是否脱敏 → 存 config，部署时填。
5. **进展唯一粒度**：默认"项目级一条 + 各节点各一条 / 人 / 天"（已落 §4.2.9 表达式唯一索引）。若允许多条，仅放宽节点级条数，项目级唯一性保留。
6. **周界定**：默认周一~周日（config `report.week_start_dow`），全系统统一；**修改周界需迁移历史 week_start 口径**。
7. **health 重算时机**：~~变更即算 + 每日定时兜底~~ → **已下线（M7）**：health 不再派生，"延期"由手动状态 delayed 表达（见 §5.2）。
8. **附件上限/类型白名单**：默认单文件 ≤ 50MB，常见文档/图片/压缩包，可配置。
9. **历史 Excel 迁移范围**：默认只迁"项目/节点/任务骨架 + 当前周目标"，历史进展不迁（降低 importx 复杂度）。若需迁历史进展，预览确认两步接口（§7.2）已支撑。
10. **成员读可见范围**：默认"看全、改己、绩效私有"（§8.3）。若需项目级读隔离，改为 member 仅见参与项目。
11. **"有条件通过"整改闭环**：默认**硬闭环**（整改任务全 done 方可进下一节点，见 §5.3 门控），承接策划书 §16-Q6；若选软标记（仅提示不阻断），移除门控即可。
12. **is_invested 时态**：默认仅存"当前是否投入"，历史周投入以"该周是否有进展/任务记录"辅助推断。若需精确按周投入，后续加 `member_invest_history` 表。
13. **审计保留期**：默认 24 个月，可配置，定期归档清理（§4.2.14）。

### 12.3 技术风险
| 风险 | 缓解 |
|---|---|
| AI 接口不稳定/限流 | 超时/重试/降级模板汇总；异步生成 + generating 状态 + 唯一键防并发 |
| 报表 SQL 复杂 | 引擎封装 + 当周快照缓存；必要时物化周快照表 |
| Excel 导入格式多样 | 模板对齐 + 映射配置 + **预览/确认两步** + 幂等键 |
| 软删与唯一约束冲突 | 统一部分唯一索引（WHERE NOT is_deleted），见 §4.2.0 |
| 跨项目数据串扰（冗余外键不一致） | 应用层写入校验（task/progress/link/attachment 的 project_id 一致性），见 §4.2 |
